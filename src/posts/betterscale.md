## 快算子之外，还有一整条执行路径

把大模型推理想成一串 GPU 或 NPU 算子，很容易得到一个直觉：只要每个算子更快，服务就会更快。但一次请求还要经过输入准备、元数据更新、任务提交、采样与状态回收。设备执行的前后，仍然存在一条由 host 和 device 共同完成的路径。

BetterScale 的起点不是重新发明一个引擎，而是在 vLLM 与 vLLM-Ascend 的既有能力上，寻找这些执行边界里值得改进的部分。原有引擎已经具备量化 GEMM、通信重叠和部分 Graph 执行能力。问题变成了：**高性能算子之间，还发生了什么？哪些准备可以提前完成，哪些依赖可以改变消费位置，哪些等待必须保留？**

这组文章主要整理项目在 2026 年 9 月的 DSV4 执行路径工作。它不是整个 BetterScale 当前能力的完整清单，也不是一次新的性能测试。

## 三个切入点

### 1. Graph 不是一个开关，而是一份执行契约

重复执行的一段程序适合被捕获成 Graph，以减少逐次提交的成本。但“支持 FULL”并不只意味着配置项写上 FULL。

捕获时的张量地址、元数据维度、请求容量以及某些标量上界，都会成为后续 replay 必须遵守的约定。Prefill、mixed 和 decode 的形状不同；真实请求数变化时，空席位如何表达也会影响契约是否成立。

BetterScale 的一部分工作就是补齐这些细节，让目标执行路径真正进入可重放的范围，而不是只在外面增加一个 Graph 包装。

### 2. 一个函数里，可能装着两种不同规模的工作

DSpark 的 draft 路径同时涉及大量 target hidden rows 的 context KV 写入，以及少量候选 query 的执行。

如果为了捕获小 query，把整个 context 都补到一个很大的桶，可能增加实际计算与内存成本。将这两种工作分开，就能让 context 按实际长度写入，让小 query 复用合适的图。

这并不意味着“拆开总是更快”。已有观察里，小 mixed 波次得到改善，大 prefill 则没有普遍加速证据。边界本身就是结果的一部分。

### 3. 需要一个值，不一定意味着现在就要等它

有些 CPU 数据决定实际访问地址，有些只是算子规划的保守上界；有些回调必须完成，但不一定要放在 target 提交之前。

在已验证的稳定 K5 波次内，可以保留 device 的精确进度与地址逻辑，同时调整 CPU 收据的消费位置。这类变化不是删除依赖，而是重新安排依赖。

尤其不能把“设备流上的执行已经有序”理解成“CPU 可以覆盖仍在 DMA 中的 pinned buffer”。执行顺序与内存所有权是两份不同的约束。

## 先看证据的层次，再看数字

这项工作里，有几类不能相互替代的证据：

| 层次 | 回答的问题 | 不能直接推出的结论 |
| --- | --- | --- |
| 同状态正确性检查 | 在指定条件下，改动是否保持输出和状态契约？ | 完整模型能力或所有配置正确 |
| 同等工作量的 matched cycle | 一段特定执行路径是否缩短？ | HTTP 服务整体吞吐同比例提高 |
| 端到端 HTTP 负载 | 给定配置和请求组合下，服务表现怎样？ | 任意流量、并发与 SLO 下都更快 |
| 容量压力测试 | 某种请求形状能否完成、资源能否回收？ | 真权重语义质量或长期稳定性 |

历史 TP8、四请求、K5 的执行路径演进可以概括为约 **65 → 52 → 46 ms/波次**。但其中包含两个分别隔离的实验：前一段约缩短 20–21%，后一段相对已优化路径再缩短 10–12%。这不是一个新的端到端 A/B，也不能把百分比直接相加。

之后的 HTTP 验收另有自己的环境、负载和版本身份。把它单独讲清楚，比把所有数字放在同一条上升曲线上更重要。

## 增量优化的价值，也在于可以不采用

项目保留了没有证明收益的方向、不利观察和质量检查的范围。实验代码存在，不等于它应当成为服务默认路径；一次更快，也不等于值得永久增加维护复杂度。

这形成了一条很朴素的工程路线：

1. 尽量保留成熟引擎已经做好的事情。
2. 找到具体边界，提出可以被验证的改动。
3. 把正确性、内存与服务表现分开测量。
4. 只保留证据支持的改进，并保留退出路径。

**少一点 host 等待，多一点 device 执行，不是靠忽略依赖实现的；它依赖于更准确地理解依赖。**
