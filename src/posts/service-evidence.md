## 不同问题，需要不同的时钟

某段 matched cycle 缩短，说明同等工作量下的一段路径更快了。但服务还包含 prefill、请求轮换、排队、首次 shape 准备，以及由生成轨迹改变带来的工作量变化。

因此，BetterScale 的 2026-09-14 HTTP 验收，没有拿历史单步时间替代端到端测量，而是比较原生 donor 与保留优化组合在具体服务负载里的表现。

这篇文章只整理已有证据，没有重新运行实验。

## 先把实验边框画出来

环境是同机 8×Ascend 910B2，DeepSeek V4 Flash W8A8、K5；软件为 vLLM 0.25.1、vLLM-Ascend 0.25.1rc1、torch-npu 2.10.0.post2 与 CANN 9.0.1。

所有程序使用 native MP executor、async scheduling 和标准 rejection，prefix cache 关闭。计时不带 profiler 或逐波证据写入。

每种程序先执行相同的短 HTTP 前导组，再执行以下三类固定输入/输出长度的合成负载，各三轮：

| 负载 | 请求安排 | 每请求输入 / 输出 |
| --- | --- | --- |
| Occupied decode | C 个请求 | 128 / 256 tokens |
| Balanced prefill | C 个请求 | 4096 / 128 tokens |
| Skew / turnover | 2C 个排队请求 | 一个输入 8192，其余 256；输出均为 128 |

DP 的 C=16，TP 的 C=4。DP 每 rank 两席位、8 GiB KV；TP 全局四席位、每 rank 12 GiB KV。最大上下文分别为 16384 和 15104。

**只比较各自拓扑内的改进。** 两种拓扑的请求并发不同，不能直接拿下面的绝对吞吐判断 DP 与 TP 谁更优。这也不是 SWE、Terminal Bench 或 OSWorld 的原始 agent 轨迹测量。

TP 基线还有一个必须保留的限定：它包含 K5/TP8 启动所必需的 LCM 兼容修复，不包含 BetterScale 的性能补丁，并非完全零修改的发行包。

## 正面结果和反面结果放在同一张表里

合计吞吐的定义是：**九组输出 token 总数 / 九组完成耗时之和**。不是九次吞吐的算术平均，也不包含组间客户端准备时间。

| Run | 程序 | 合计输出吞吐（tok/s） | 相对本拓扑原生 |
| --- | --- | ---: | ---: |
| 158 | DP8 native | 268.89 | 基线 |
| 159 | DP8 0.3.0 源码路径 | 252.47 | −6.11% |
| 155 | DP8 已验收启动预热实现 | 375.45 | +39.63% |
| 160 | TP8 native + LCM 修复 | 155.13 | 基线 |
| 161 | TP8 0.3.0 源码路径 | 209.68 | +35.17% |

DP 0.3.0 没有整体胜出，不能因为存在一个更好的 DP 实验版本，就把发布版的结果改写成正收益。启动预热程序 run155 是同机之前已经完成的测量，后来其实现收进了 0.3.1；**+39.63% 是复用已验收实现的既有成绩，不是对 0.3.1 wheel 的新一轮硬件测量。**

TP 的 +35.17% 也属于表中明确的程序、负载和对照，而不是任意流量下的保证。

## 吞吐提高，不等于所有延迟都改善

TP 优化路径的 prefill 和轮换负载表现更好，但 occupied decode 的尾部延迟并非如此：各轮输出 chunk 间隔 P99 的中位数，从基线的 0.069 s 变成了 0.203 s；TTFT P95 的中位数从 0.486 s 变成 0.645 s。

这里的 chunk 间隔是 HTTP 流式输出的观测量，不等于模型 step 时间，也不是逐 token TPOT。三个轮次分位数的中位数，也不是把三轮样本合并后重新计算的分位数。

这类定义看似琐碎，却决定“延迟更好”究竟有没有被证据支持。表里有合计吞吐提升，仍然不能写成“全面改善用户体验”。

## 冷启动成本不能凭喜好删掉

加载、初始化、前导组与质量验收不计入九组计时；但 READY 后仍可能发生的首次 shape/capture 成本没有删除，较慢的首轮也被保留。

DP 0.3.0 首轮三类负载均明显偏慢，源码还存在首次遇到 shape 时的辅助图构建。不过，本轮没有新增 timeline 来逐一归因，所以不能仅凭这一现象断言全部差异都由 capture 导致。

这组测量还存在几项统计限制：

- 三轮发生在同一个进程中，不是三次独立启动；
- 各程序依次运行，没有随机化顺序；
- 启动预热的 run155 早于本轮其他程序，明确属于复用数据；
- 样本范围有限，没有形成任意生产流量的 SLO 认证。

保留这些限制不是抵消正面结果，而是让别人知道可以把结果用在哪里。

## 质量门通过了什么，又没有通过什么

五个程序都完成了保留的 32 道原始长上下文检索题，在指定 OpenCompass evaluator 下得到 32/32。

这是一项有价值的质量门，但不是完整 OpenCompass suite，不是全模型精度认证，也不是新一轮全 KV 逐字节 shadow 检查。性能计时、语义质量与状态一致性，各自回答不同问题。

## 一份可用的性能结论应该长什么样

这次验收支持这样的表述：在上述有限同机 HTTP 工作负载中，保留 TP 路径与已验收 DP 启动预热实现分别提升了各自拓扑内的合计输出吞吐；所有测量程序通过该 32 题检索门，但延迟尾部没有普遍改善。

它不支持这样的表述：“BetterScale 在所有场景都快 35%–40%”，或“单步优化已经证明生产服务全面更好”。

**结论的边界不是脚注，而是结论本身。**
