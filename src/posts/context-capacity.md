## “支持 512K”还没有回答容量问题

看到 `max-model-len=524288`，再看到配置有四个活跃请求席位，很容易把它理解成“可以同时服务四个 512K 请求”。这两个数字相乘，却未必对应真实的物理资源。

最大长度描述单请求输入加输出的上限；席位描述可活跃请求数上限。两者都不等于为所有请求预留了最大长度的缓存空间。长请求仍可能因实际容量而排队。

BetterScale 0.4 的容量记录，首先强调的是把下面四个量分开。

| 数字 | 它回答的问题 | 不应当被解释成 |
| --- | --- | --- |
| 物理 KV 字节 / rank | 这个 rank 实际拿到多少缓存预算？ | 整机独立可用 token 数 |
| 最大模型长度 | 单请求最多允许多长的输入加输出？ | 每个请求都有这份预留内存 |
| 活跃请求席位 | 调度最多允许多少请求同时活跃？ | 最大长度请求可全部同时驻留 |
| 原生日志的 KV tokens | 当前 horizon 下混合缓存的等效容量是多少？ | 永远不变、可直接相乘的 token 槽数 |

## 自动定容不是换一个显存百分比

在没有显式设置 `--kv-cache-memory-bytes` 时，0.4 的路线是先测量完整执行程序的驻留成本，再把实际可用余量交给原生缓存管理器。用户明确指定固定字节预算时，仍保留手工路径。

完整执行程序的驻留，不只有模型权重。Graph、metadata、state 以及 eager / non-Torch 部分都需要空间。记录中的 target/draft 使用同一个 Graph 池，并保留约 1 GiB/rank 安全量，而不是把设备空闲压到零。

这是根据真实驻留做预算，不是把常见利用率参数从 90% 换成另一个更激进的百分比。其他进程在定容后抢占设备资源，也不在这个算法的仲裁范围内。

## 混合缓存不能简化成固定 token 槽

SWA 有滑窗回收，但滑窗长度并不是全部驻留状态。较大的 prefill 波次还会影响滑窗与 compressor 峰值，不同缓存组还共享分配约束，并承担对齐和 padding 成本。

因此，原生日志给出的混合缓存等效 token 数需要结合当时 horizon 解读，不能脱离模型缓存结构直接换算并发承诺。

这轮容量工作没有改变原生 KV 布局、哈希协议或 TP 复制关系，也没有开启 APC。不能把它叙述成一次新的缓存压缩算法，或前缀缓存收益实验。

## 三类记录，各自说明什么

### TP 真权重：已有一定容量与质量证据

Run190 的自动 KV 预算约为 14.939–14.948 GiB/rank，READY 后约剩余 0.965–0.974 GiB/rank 空闲。

该程序通过 32 道原始长上下文检索题，完成一个 60K 输入以及八个 8K 输入的周转。这支持对应程序与形状的容量和质量观察，不是完整 OpenCompass 验收，也不是一次新的原生 baseline 吞吐对比。

### TP dummy：压力能完成，不等于语义质量已认证

Run188/189 完成单 448Ki 输入、四个 128Ki 输入，以及四个 448Ki 输入、各生成 2048 token 的压力队列。这里 Ki 表示 1024 的倍数，不是十进制 K。

值得注意的不是只有“完成”二字：四个很长的请求最多三个同时运行，第四个排队。最高 KV 占用为 96.84%，随后十六个 8K 请求也完成，记录的运行期额外分配峰值约为 326 MiB/rank。

这证明的是该 dummy 模型测试形状下的容量、周转与回收，不是真权重吞吐，也不是长上下文语义质量。它同时给出了“席位不等于全长并发”的实际例子。

### DP 真权重：部分通过，较重队列没有完成验收

Run170/171/174 的自动 KV 约为 7.9 GiB/rank，32 题检索通过，八个 60K 输入完成；另一个 512K 配置下，单 448Ki 输入也完成。

但随后更重的队列达到外层时间上限。**超时不能改写成 OOM，也不能忽略后宣布长历史满池服务验收通过。** 它只说明，在已记录的条件和期限内，这部分验证没有完成。

## 高占用率也不能证明另一条失败路径已经修复

历史 3 GiB 诊断预算下存在抢占恢复失败。后来的高占用压力测试没有发生抢占，所以即使峰值达到 96.84%，也不能据此认定抢占路径已被修复。

这是一个常见的验证误区：测试整体压力更大，并不意味着它覆盖了所有特定故障机制。要验证抢占恢复，就需要真正触及那条状态转换，而不只是更接近内存上限。

## 描述容量时，保留一组完整坐标

与其写“支持 512K，支持四并发”，不如给出：

- 模型、权重类型与并行布局；
- 每 rank 物理预算、执行驻留与安全余量；
- 请求长度、输出长度、队列与实际同时活跃数；
- 是否发生排队、抢占、超时或 OOM；
- 使用真权重还是 dummy，质量门覆盖了什么。

这些信息让容量结论可以复用，也让下一次验证有明确的起点。**配置告诉我们想允许什么，运行证据才告诉我们已经验证了什么。**
